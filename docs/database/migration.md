# Migrations

## Configuration

Prisma 7 no longer accepts a `url` in `schema.prisma`'s `datasource` block — connection
configuration for Migrate lives in `prisma.config.ts` instead:

```ts
export default defineConfig({
  schema: 'prisma/schema.prisma',
  migrations: { path: 'prisma/migrations', seed: 'tsx scripts/database/seed.ts' },
  datasource: { url: process.env.DATABASE_URL },
});
```

`DATABASE_URL` comes from `.env` (loaded via `dotenv/config` at the top of `prisma.config.ts`).
`migrations.seed` is what `prisma db seed` and `prisma migrate dev` (when they create a new
migration) run. In this Prisma 7.10.0 setup, `prisma migrate reset --force` did **not** reliably
auto-run it when invoked non-interactively (observed while verifying this phase) — so `db:reset`
explicitly chains `npm run db:seed` afterwards rather than depending on that behavior.

## Applying migrations

```sh
npm run db:up             # docker compose up -d (PostgreSQL + pgvector)
npm run db:migrate        # prisma migrate deploy — applies pending migrations, no prompts
```

`db:migrate` uses `prisma migrate deploy`, not `prisma migrate dev`: `deploy` only applies
existing migrations and never generates a new one, which is what a reproducible "empty database
-> migration -> complete schema" flow needs (and what CI should use). `db:reset` (`prisma migrate
reset --force`) drops the database, re-runs every migration from scratch, and re-seeds — the way
to prove the migration truly is reproducible from empty.

## The initial migration

`prisma/migrations/<timestamp>_init/migration.sql` is Prisma-generated (`prisma migrate dev
--create-only` against `schema.prisma`) **plus** hand-authored SQL appended for everything
Prisma's schema language cannot express declaratively:

| Addition | Why it's hand-authored |
| --- | --- |
| `CREATE EXTENSION IF NOT EXISTS vector;` | No extension-enablement syntax used (kept deliberately simple; see architecture.md) |
| `DEFERRABLE INITIALLY DEFERRED` on the two departments cyclic FKs | No `DEFERRABLE` attribute in `schema.prisma` |
| `CHECK` constraints (inventory invariant + non-negativity, approval-tier bounds, positive ordinals, exactly-one-target on `scenario_entities`/`evaluation_question_sources`, ...) | No declarative `CHECK` syntax in `schema.prisma` |
| Two partial unique indexes on `scenario_entities` | No `WHERE` clause support on `@@index` |

Every hand-authored statement has a comment in the migration file explaining what it does and
pointing back to `architecture.md`. **None of these are represented in `schema.prisma`** — that
is deliberate: Prisma's migration diffing works by replaying migration history against a shadow
database and comparing it to what `schema.prisma` describes. Because `schema.prisma` has no way
to express `DEFERRABLE`, `CHECK`, or partial indexes, it never "notices" they're missing and
never generates a migration to remove them. This is the same reasoning documented in
architecture.md for choosing a `CHECK` constraint over a `GENERATED ALWAYS` column.

**Consequence for future schema changes:** if you add a column to one of the tables above (or
otherwise touch its `CREATE TABLE`/`ALTER TABLE`), run `prisma migrate dev --create-only`,
inspect the generated SQL, and re-add any hand-authored constraint that new migration doesn't
already carry forward via Postgres's own state (constraints on existing columns aren't dropped
by an unrelated `ADD COLUMN`, so most changes need no extra care — only a migration that
recreates or drops one of the tables above would).

## Verifying "empty database -> migration -> complete schema"

```sh
npm run db:reset          # drops svga_enterprise, re-creates it, re-applies every migration, re-seeds
npm run db:validate
```

This was run as part of this implementation (see the final report); `db:reset` is the
repeatable way to re-prove it later.

## Prisma Client generation

`prisma generate` writes the client to `apps/src/generated/prisma/` (gitignored — regenerated by
`postinstall` and by `npm run db:generate`). `schema.prisma`'s `generator client` block points
there explicitly:

```prisma
generator client {
  provider = "prisma-client-js"
  output   = "../apps/src/generated/prisma"
}
```

Both `scripts/database/lib/client.ts` (used by the seed/validate scripts) and
`apps/src/database/prisma.service.ts` (used by the NestJS app) construct `PrismaClient` with the
`@prisma/adapter-pg` driver adapter (`new PrismaPg({ connectionString })`) rather than Prisma's
historical query-engine binary — Prisma 7's default architecture.

## Iterating on the schema during development

For day-to-day schema changes (not covered by the npm scripts, which are the "just apply /
reset" commands):

```sh
npx prisma format             # canonicalize schema.prisma formatting
npx prisma validate           # check schema.prisma without touching the database
npx prisma migrate dev --name <change>   # create + apply a new migration, regenerate the client
```
